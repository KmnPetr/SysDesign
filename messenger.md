## Функциональные требования

## Нефункциональные требования

- **DAU** до **1 000 000** пользователей
- **350** слов в день на пользователя
- **1** картинка (~**300** KB) + **1** видео (~**30** MB) в сообщении
- медиафайлы хранятся **1** месяц

  | Операция (по User Cases) | / пользователь / день | / 1M / день |
  | --- | --- | --- |
  | **GET** `/api/chat/all` (п. 1) | **~7** | **7 000 000** |
  | **GET** `/api/message/all` (п. 4) | **14** | **14 000 000** |
  | **GET** `/api/user` (п. 4) | **14** | **14 000 000** |
  | **SELECT** `user`, `chats`, `chat_members` при п. 1 (×7) | **21** | **21 000 000** |
  | **INSERT** `messages` (п. 6) | 18 | 18 000 000 |
  | **INSERT** `attachment` (п. 6, медиа) | 1 | 1 000 000 |
  | **UPDATE** `chat` `count_msg`, `last_msg_id` (п. 6) | 18 | 18 000 000 |
  | **UPDATE** `chat_members` при отправке (п. 6) | 18 | 18 000 000 |
  | **UPDATE** `messages` прочитанность, сравнение `id` (п. 5, 7) | 5 | 5 000 000 |
  | **UPDATE** `chat_members` `count_read` (п. 5, 7) | 5 | 5 000 000 |
  | **UPDATE** `attachment` после загрузки (п. 6) | 1 | 1 000 000 |
  | **Итого** операций к БД и HTTP | **122** | **122 000 000** |

  *`subscribe`, `typing`, redis/kafka — без строк в Postgres; в RPS не входят.*

  **Расчет RPS, RPM** — **122 000 000** операций/сутки на **1M** DAU.

  | | | | RPS | RPM |
  | --- | --- | --- | --- | --- |
  | Пиковые значения (8 часов) | 60% трафика | 73 200 000 оп | **2 542** | **152 500** |
  | Обычный день (8 часов) | 30% трафика | 36 600 000 оп | **1 271** | **76 250** |
  | Ночь (8 часов) | 10% трафика | 12 200 000 оп | **424** | **25 440** |

  *RPS = операции_периода ÷ (8 × 3600); RPM = RPS × 60 (как в `architecture.md`).*

  *Оценка при **DAU** 1M. Текст: ~**4** GB/день (350 слов). За 30 дней — верхняя граница накопления.*

  | Масштаб | Текст (~350 слов/день) |
  | --- | --- |
  | 1 пользователь / день | **~4** KB |
  | 1M пользователей / день | **~4** GB |
  | 1M пользователей × **30** дней | **~120** GB |
  | 1M пользователей × **1** год | **~1,5** TB (~**8** серверов Postgres при **~200** GB на инстанс) |

  *Медиа: 1×300 KB и 1×30 MB на пользователя в день. За 30 дней — верхняя граница, если весь суточный объём хранить месяц.*

  | Масштаб | Картинки | Видео |
  | --- | --- | --- |
  | 1 пользователь / день | **300** KB | **30** MB |
  | 1M пользователей / день | **~0,3** TB | **~30** TB |
  | 1M пользователей × **30** дней | **~9** TB | **~900** TB (диск **~20** TB; **~12** дисков/сервер ≈ **~150** TB полезно → **~6** storage-серверов) |

## User Cases

## 1) получение первичных данных (http)

*Почему http? ожидать и кеш при открытии: запрос по чатам идёт на центральный сервер хранения users и chats.*

- клиенту показывается старый список чатов из кеша его устройства
- http на центральный на получение агрегированного json-сообщения с информацией по всем чатам

  ```http
  GET https://msgmain.<host>.com/api/chat/all/{userId}
  ```

  **Responce:**

  ```json
  {
    "user": {...},
    "chats": [...],
    "chat_members": [...]
  }
  ```

  - сервер получает из БД:
    - список актуальных чатов пользователя из таблицы **`user`** поля **`chats`**
    - список **`chats`** обьектов из таблицы <mark><em>#TODO возможно надо отделить поле **`users`** от таблицы **`chats`**, при 1млн. подписчиков будет слишком длинная запись</em></mark>
    - список обьектов **`chat_members`** для подсчета клиентом количества непрочитанных
    
- пользователь получает евентом агрегированный обьект списка чатов с актуальной информацией (имена / названия каналов, ссылки на иконки, кто online, количество прочитанных **`msg`**)

## 2) установка socket

- при установке socket, сервер связывает обьект **`user`** и обьект socket (со списком `chat_ids:[...]` для удобства его удаления подписчика при разрыве соединения), хранит их в памяти процесса сервера

  ```
  wss://msg<server_id>.<host>.com/
  ```

  **event:**

  ```json
  {
    "type": "subscribe",
    "chats_ids": [
      <chat_id>, <server_id>,
      <chat_id>, <server_id>,
      ...
    ] //limit 100
  }
  ```

- сервер в кеш-redis добавляет нового **`sub`** во все чаты согласно полученному списку чатов текущего сервера (в том числе чаты чужего сервера) (за получением чата нежелателен запрос в бд)
- если чат принадлежит другому серверу, отправляется сообщение в кафку

  **kafka event:**

  ```json
  {
    "pub_server_id": 2, #topic key
    "sub_server_id": 1,
    "type": "subscribe",
    "chat_id": 1234,
    "type_chat": "private / group",
    "count_users": 19 // At Most Once (сколько бы ни было подписано юзеров, второй сервер будет присылать евенты по 1 екземпляру)
  }
  ```

- сервер разсылает **`event`** уведомление во все локальные сокеты пользователи которых подписаны на эти чаты чаты что пользователь online

  **online event:**

  ```json
  {
    "type": "online",
    "chat_id": 1234,
    "count_subs": 12 #private chat - покажет что пользователь онлайн, group - покажет количество в онлайне
  }
  ```

## 3) разрыв сокет соединения

- пользователь выходит из приложения, соединение разрывается
- сервер onClose() у обьекта сокета, смотрит запись **`user`** -> **`chats[]`**
- из всех групп удаляется **`id`** пользователя в кеше, убирается подписка
- если чат с чужего сервера, отправляется евент в кафку

  **kafka event:**

  ```json
  {
    "pub_server_id": 2, #topic key
    "sub_server_id": 1,
    "type": "unsubscribe",
    "chat_id": 1234,
    "count_subs": 0 #если 0 - At Least Once, если остались пользователи, сообщение может не отправляться с определенной вероятностью
  }
  ```

- оба сервера на все свои локальные чаты на которые был подписан пользователь отправляется **`event`** (**`user ofline`**) + **`last_visit_time`**

  **local event:**

  ```json
  {
    "type": "ofline",
    "chat_id": 1234,
    "count_subs": 0 #если 0 - At Least Once, если остались пользователи, сообщение может не отправляться с определенной вероятностью
    "last_visit_time": "..."
  }
  ```

## 4) пользователь заходит в выбранный чат

*Почему именно http? сервер, который хранит массив сообщений, — не тот, к которому пользователь подключён по socket.*

- пользователь загружает старое состояние из своего кеша (по кешу определяет id сервера чата)
- посылает http запрос на получение списка сообщений

  ```http
  GET https://msg<server_id>.<host>.com/api/message/all/<chat_id>
  ```

  **Responce:** `[...list messages...]`

  ```http
  GET https://msgmain.<host>.com/api/user/<user_id>
  ```

  **Responce:**

  ```json
  {
    "user": {
      "last_seen": "<time miliseconds>"
    }
  }
  ```

- **`chat_members`**, **`count_subs`**, были получены ранее

## 5) пользователь пролистывает список сообщений вниз

- пользователь отсылает список **`id`** прочитанных сообщений + **`count_msg`** которое он ранее получил

  **event:**

  ```json
  {
    "type": "read_msgs",
    "chat_id": 1234,
    "server_id": 2, #topic key
    "msgs_ids": [...],
    "count_read": 248,
    "last_read_msg_id": 2345
  }
  ```

- если чат на другом сервере, это же сообщение без изменений можно переслать в кафку
- сервер смотрит в кеше **`chat`** если есть подписчики, отсылает **`event`** (**`read message`** + список **`id`**)
- сервер находит сообщения и обновляет статус прочитанности (или пишет в кафку на центральный сервер чтобы эта информация обновлялась лениво пачками)
- сервер записывает в **`chat_members`** **`id`** последнего сообщения и **`count_read`**

## 6) пользователь создает новое сообщение

  **event:**

  ```json
  {
    "type": "new_msg",
    "server_id": 2, #topic key
    "local_id": null,
    "chat_id": 1234,
    "text": "Привет! Как дела?",
    "meta": {
      "files": ["image.png", "file.txt"],
      "sizes": [248000, 3000]
    }
  }
  ```

- если нет медиафайла
  - создается евент (**`create message`**)
  - сервер записывает в таблицу **`messages`** новое сообщение
  - сервер записывает в таблицу **`chat`** **`count_msg`** + **`last_msg_id`** (поскольку массив сообщений одного чата храниться на одном сервере достаточно проверить по **`id`** порядок)
  - сервер обновляет **`chat_members`** (чтобы потом не появлялось иконки непрочитанного сообщения)
  - сервер отправляет **`event`** (**`new message`**) в чат на который есть подписчики, если нет то в push service
- если есть медиафайлы
  - создается евент (**`create message`**)
  - сервер записывает в таблицу **`messages`** новое сообщение + **`attachment`** (по количеству вложений)
  - сервер отсылает в сокет пользователю евент (**`signal load file`** + **`attachment_id`**)

    **event:**

    ```json
    {
      "type": "signal_load_file",
      "attachments_ids": [...]
    }
    ```

  - пользователь производит загрузку файлов по https
  - сервер после успешной загрузки, сервер изменяет статусы загруженности **`attachment`**
  - сервер отправляет **`event`** (**`new message`**) в чат на который есть подписчики, если нет то в push service

- если чат на другом сервере, перессылка евентов идет через кафку, теже евенты но с дополнительными полями id серверов

## 7) прочтение нового сообщения (при получении евента нового сообщения во время просмотра чата)

- пользователь отсылает список **`id`** прочитанных сообщений + **`count_msg`** ранее полученный из чата

  **event:**

  ```json
  {
    "type": "read_msgs",
    "chat_id": 1234,
    "server_id": 2, #topic key
    "msgs_ids": [...],
    "count_read": 248,
    "last_read_msg_id": 2345
  }
  ```

- сервер записывает в **`chat_members`** **`id`** последнего сообщения и **`count_read`**

## 8) редактирование сообщения

- пользователь отсылает **`event`** (**`edit message`**) в сокет

  **event:**

  ```json
  {
    "type": "edit_msg",
    "server_id": 2, #topic key
    "chat_id": 1234,
    "msg_id": 2345,
    "text": "Привет! Как дела?"
  }
  ```

- сервер делает апдейт записи **`message`**
- сервер обновляет поле **`count_msg`** + 1 в таблице **`chat`**
- сервер отправляет **`event`** (**`new message`**) в чат на который есть подписчики, если нет то в push service

## 9) удаление сообщения

- пользователь отсылает **`event`** (**`delete message`**) в сокет

  **event:**

  ```json
  {
    "type": "delete_msg",
    "server_id": 2, #topic key
    "chat_id": 1234,
    "msg_id": 2345
  }
  ```

- сервер удаляет сообщение из таблицы
- сервер обновляет поле **`count_msg`** - 1 в таблице **`chat`**, поле **`last_msg_id`** поставит null чтобы не искать предыдущее сообщение
- сервер отправляет **`event`** (**`delete message`**) в чат на который есть подписчики, в push service ничего не отправляется

## 10) typing...

- при печати с клавиатуры отсылается **`event`** каждые 5 секунд, события отмены нет

  **event:**

  ```json
  {
    "type": "typing",
    "server_id": 2, #topic key
    "chat_id": 1234
  }
  ```

- сервер перенаправляет евент на сокеты подписчиков этого чата из кеш-redis
